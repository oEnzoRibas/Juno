---
name: juno-independent-review
description: Independently qualify a pinned Juno candidate and report reproducible platform and regression evidence. Use for independent QA, release readiness evidence, or integration handoffs.
---

Confirm the assigned scope, exact head, base or included parents, and reviewer independence. Keep your validation separate from the implementation worktree and report any overlap in authorship. Read the [maintainer review standard](../../../docs/development/git-workflow.md#maintainer-review-standard) and applicable [quality gates](../../../docs/testing/README.md). Use [juno-review-environment](../juno-review-environment/SKILL.md) if building or recovering an isolated runtime.

1. Inspect the pinned candidate's [Compose validator](../../../scripts/quality/validate-compose.mjs). Follow the fixture list it uses and check that each required SQL fixture runs once. Identify fixtures present on disk but missing from the runner or its output. Use the candidate's standard validator or review launcher where applicable.
2. Separate runtime/API assertions from UI checks. Exercise affected negative tenant and role cases with synthetic data. For concurrent directorate creation introduced by [#133](https://github.com/oEnzoRibas/Juno/pull/133), verify one success and one conflict, then verify one persisted directorate and one audit event attributed to the expected actor. Confirm SQL coverage for isolation and rollback when the audit write fails. Apply the corresponding persisted-audit check for concurrent profile writes when in scope.
3. Read the command exit, named SQL assertions, structured browser summary, actual hosted jobs and cleanup results. A successful standalone run covers its own head and runtime. Name any missing sibling prerequisite and record a separately pinned composition when needed. Use the existing [recovery](../../../docs/testing/juno-database-recovery.md) or [production installation qualification](../../../docs/testing/juno-production-installation.md) only for relevant recovery work.
4. Report exact SHA and tree, source inputs and bases, commands, runtime/provenance, scope and result counts, failures and skipped checks, limitations, and the next owner action. Distinguish independent local evidence, implementation-owner results, hosted results, and human acceptance. Describe re-runs with changed setup as separate observations. Omit credentials, session values, private fixture files and sensitive response bodies. Publish in the authorized review channel.
