# Operating a bounded Juno assignment

## Decide whether to delegate

Agent 01 checks whether an independent deliverable can finish without writing the same path, consuming a reserved port or deciding another lane's contract. If the task is small, requires a sequence of dependent decisions, or lacks a testable output, assign it to one owner. If it has separable deliverables, identify the join and the independent verifier before dispatch. Each child receives only its task and returns to the owner. Nested delegation needs a new scoped decision and reservation.

## Dispatch, repair and handoff

1. Read the [project protocol](../../PROTOCOL.md) and [registry](../../agents/ASSIGNMENTS.md). Confirm the issue, active owner and worktree. Resolve remote base and head using Git. Inspect tracked, staged and untracked changes. Keep existing user work and UAT environments intact.
2. Write the contract with objective, requirements, owner, dependencies and exact revisions, read-only inputs, writable paths, expected artifacts, skill versions and tools. Set acceptance, required checks, permission limits, current state, blockers and recovery steps. Give each attempt a distinct identifier. Include time or resource limits and a stop condition.
3. Validate dependencies, ownership and resource overlap. Dispatch only eligible tasks. For example, a change to one API field can first produce a frozen OpenAPI contract. Separate backend and frontend tasks may then share that contract as read-only. Their integration task waits for both implementation pins. Publish the scoped assignment and confirm receipt before reallocating its resources.
4. Provide the objective and mandatory policy, acceptance and permissions directly. Point to exact paths for implementation details. Fetch optional references on demand. Request the smallest reproducible test for the specified error, capture its failing result, implement within scope, rerun it and the affected regression suite. For a new behavior, check the test's pre-change failure reason in the isolated tree.
5. After failure, retain the command, exit, unexpected result and input revision. Identify one falsifiable cause before retrying. For pilots, allow two repair attempts after the initial failure, bounded by the contract's lower time or resource limit. A repeated identical failure without a new diagnostic or an exhausted budget returns a blocker. Hold writes immediately on ownership conflicts, scope changes, missing dependencies, security-sensitive policy, destructive operations or human product decisions.
6. Publish the [handoff](../../agents/HANDOFF_TEMPLATE.md) with exact base/head, affected paths, outputs, test results and failures, provenance, pending gates and next action. Use the [#125 checkpoint verifier](https://github.com/oEnzoRibas/Juno/blob/a0e0a393b3e71d658fe29b55a6671cb49d087023/docs/development/harness/checkpoint.md) at its pinned revision. A pending or rejected receipt keeps the reservation with the current owner.
7. Give a separate reviewer the pinned candidate, public acceptance and environment instructions. For runtime work, use the [review launcher](../../../../scripts/review/README.md) and [runtime identity checks](../../../testing/juno-review-runtime.md). Compare required SQL with actually executed names and counts, check actual web-to-API connectivity, schema and relevant denial cases, and preserve the original failed run. Reproduce the integrated composition when the contract spans PRs.
8. Agent 01 reconciles dependencies and exact reviewed artifacts before publication. Record the author, independent reviewer, hosted CI and human disposition separately. Return unresolved claims to the original owner. Subsequent revisions invalidate earlier exact-head claims until rechecked.

## Restore an interrupted assignment

Inspect the last acknowledged handoff, assignment, local changes, remote head and live processes. Match all to the checkpoint. If clean and consistent, reconstruct mandatory context, rerun a cheap identity or fixture check and resume at the first incomplete step. If the branch moved, preserve both pins and have the owner reconcile. If the interrupted run produced an artifact without an exit or acknowledgement, verify it or rerun the minimum safe step with a new attempt ID. Never release a lock, terminate an unrelated process or rewrite a protected worktree as part of recovery.

## Model and resource allocation experiment

The desktop delegation surface for this investigation advertised `gpt-6.2-astra`, `gpt-6.2-sol`, `gpt-6.1-terra`, `gpt-6.1-sol` and `gpt-6-astra`; advertised reasoning efforts were low, medium, high, xhigh, max and ultra. Availability is an interface observation. Record the effective model/effort from each run when exposed. Treat an unreported effective setting as unknown. The five #123 role TOMLs inherit parent defaults.

Use Astra for the principal architecture decision, complex decomposition, cross-system diagnosis and synthesis in this intervention. Keep the main topology experiment on one pinned model and effort. Then vary model assignments separately, e.g. Sol for small, specified implementation or review, Terra for rendered evidence, and deterministic scripts for revision identity, coverage, migration checks, receipt validation and formatting. Give a second model a specific unresolved question only when evidence warrants escalation. Record the reason and include both attempts in cost and time.

For the pilot, set concurrency to 1, 2 or 3 **active implementation owners**, respecting disjoint registry claims and the host's lower effective limit. Count the coordinator, idle owners, verification workers and elapsed wait separately. For comparable short cases, start with a 20-minute wall limit per attempt and two repair attempts, then predeclare case-specific limits before assignment (especially end-to-end builds). Use the same limits within a matched block. Log tool calls, subagent time, bytes/estimated tokens of context and actual token usage when reported. An elapsed deadline is enforceable even if token counters are unavailable. No billed API service is an assumed dependency. These are trial settings, not evidence of an optimum.

## Maintainer review

Check the PR's parent and exact head. Inspect the registry, intended diff and fresh evidence in the pinned tree. Ask whether each required check executed and whether the author and verifier are distinguishable. If a human decision is needed, record which artifact, revision and decision the authorization covers. Human authorization is required for merge, release, production changes, destructive actions, persistent trust changes, newly billed dependencies, external disclosure beyond the agreed channel, and product or aesthetic decisions reserved to the maintainer.

A rejection records the failing criterion and returns the work to its owner. A reissue names the new revision and required reruns. Suspend a problematic experimental path by retaining the prior V1 workflow and its historical receipts; preserve experimental logs for analysis.
